**Статус: подготовка к проверке, не разрешение на установку или переключение сайта.**
Основа: `timeweb-static`, commit `de094b9dfc9848a0e47e7ef65d941de4843c047c`.
Ни одна команда ниже не запускалась на рабочем Supabase Cloud или Tatnet.
Все существующие аккаунты и данные остаются в исходном проекте. Переноса пользователей,
паролей, Google identities, записей, посещений, аватаров или тестового контента нет.

`install.sql` не является обновлением существующей БД и намеренно не допускает повторной установки.

## Что устанавливается

22 таблицы: 19 актуальных таблиц приложения из истории репозитория, две публичные
проекции CMS и закрытый флаг приостановки бронирования. Списки столбцов, ограничений,
индексов, триггеров и функций — в `install.sql`; RLS включён на всех таблицах приложения.

| Область | Таблицы |
|---|---|
| Аккаунт и права | `profiles`, `user_roles` |
| Встречи и посещения | `meetups`, `meetup_bookings`, `attendance`, `attendance_admin_notes` |
| Награды | `loyalty_rewards`, `special_rewards`, `special_reward_admin_notes` |
| Вопросы | `managed_questions`, `question_progress`, `question_favorites`, `question_deck_state` |
| CMS | `site_content`, `site_faq_items`, `site_content_revisions`, `media_assets`, `site_content_public`, `site_faq_public` |
| Уведомления и аудит | `notifications`, `admin_audit_log` |
| Закрытая настройка | `app_private.privacy_protection_control` |

28 функций, 38 триггеров и 78 политик в сгенерированном установщике.
Схемы `auth`, `storage`, `realtime` должны быть предоставлены платформой; их реализацию
установщик не заменяет. Старые live-only таблицы `user_profiles` и `user_question_history`
не копируются. Расширения `pg_cron` и `pg_net` этому установщику не нужны.

Единственные начальные строки: два описания buckets и `paused=true`. Нет участников,
встреч, бронирований, посещений, наград, вопросов или CMS-записей. Встроенные вопросы,
FAQ и статические значения сайта остаются в исходниках приложения. Редактор CMS изначально
пуст; наполнение проверенным неперсональным контентом — отдельное действие.

### Изменения безопасности

- Каждый новый Auth user получает только `member`. Нет автоматического admin по email
  или `user_metadata`; максимум один admin обеспечивает уникальный частичный индекс.
- Запись `user_roles` запрещена всем браузерным клиентам, включая admin. Существующие
  кнопки изменения ролей в админке не смогут повысить права: это намеренное ограничение.
  Замена администратора требует отдельной согласованной процедуры владельца БД.
- Нет клиентских `TRUNCATE`, `TRIGGER`, `REFERENCES`, `CREATE public` и универсального `ALL`.
  `profiles.email` доступен для чтения владельцу/admin, но не для клиентской записи.
- Получатель уведомления может изменять только `read_at`, а не текст, ссылку или адресата.
- Черновики CMS доступны только admin; публичные физические проекции содержат исключительно
  опубликованные поля. Триггеры синхронизируют публикацию, снятие с публикации и удаление.
- Гостевой каталог вопросов не вызывает приватную admin-функцию; гостевые встречи требуют
  `is_public=true`. Публичные и административные правила разделены.
- Аватары приватные: владелец может загружать свой путь, подтверждённый admin — читать;
  `site-media` публичен для чтения, запись — admin. Нет импорта старых файлов.
- Private Realtime topic `question-state:<UUID>` доступен своему подтверждённому пользователю.
- SECURITY DEFINER функции используют пустой `search_path`, явные схемы и необходимые проверки.
  Service-role/владелец БД остаются доверенными привилегированными операторами; в браузер их ключи запрещены.

**Связанный контракт приложения:** [home-page.tsx](../../src/components/home-page.tsx)
и [footer.tsx](../../src/components/footer.tsx) читают `site_content_public`.
Текущий Cloud может не иметь этой таблицы. **Не выпускать эту сборку с прежней БД**:
изменения приложения и новая БД проверяются вместе. Не делать небезопасный fallback к черновикам.
`site_faq_public` подготовлена для публикации; текущая публичная FAQ использует встроенный контент.
CMS не является источником всех страниц. Исторические миграции не изменены.

## 1. Обязательная проверка Tatnet перед разрешением на установку

Пока **не подтверждено на конкретном Tatnet-проекте**:

1. Это именно управляемый **Supabase**, а не обычный PostgreSQL. Записать URL/ref нового
   проекта и визуально отличить его от рабочего Cloud; ключи не сохранять в репозитории.
2. SQL Editor допускает транзакцию целиком и создание `app_private`, функций SECURITY DEFINER,
   RLS, триггеров на `auth.users`, buckets, политик Storage/Realtime и необходимых grants.
   Нужна роль владельца, а не клиент `authenticated`. Уточнить у поддержки ограничения DDL.
3. Доступны `auth.uid()`, `auth.jwt()`, `realtime.send(jsonb,text,text,boolean)` и `realtime.topic()`;
   формат JWT, подтверждённость email, Auth/Storage API и private broadcast совместимы с приложением.
4. Пустой проект проходит preflight: нет Auth users, public relations, `app_private`, пользовательских
   Auth-триггеров, Storage buckets/objects и Storage/Realtime policies. Конфликтующие public RPC
   также блокируются. Если платформа создаёт собственные политики/триггеры, **не удалять их**:
   получить их описание у поддержки и пересмотреть совместимость установщика.
5. В Auth UI можно запретить публичный signup, сохранив вход и приглашение/создание владельцем.
   SQL-установщик **не закрывает Auth signup API**. Это отдельная настройка платформы.
6. Проверить email/password, SMTP, подтверждение email, восстановление пароля, CAPTCHA/Turnstile,
   redirect allowlist и URL callback/recovery на согласованном тестовом origin.
   Не отключать CAPTCHA или подтверждение email ради прохождения проверки.
7. Проверить тип публичного ключа Tatnet с `scripts/validate-auth-config.mjs` и текущим browser SDK.
   Поддержка нового `sb_publishable_*` платформой сама по себе не доказывает совместимость build gate.
   Если есть расхождение — отдельная проверяемая правка, без подстановки service-role ключа.
8. Проверить тарификацию, резервные копии и восстановление именно Supabase-проекта. Наличие
   SQL Editor не доказывает доступность PostgreSQL backup/restore или внешнего `psql`.

Официальные точки проверки: [Supabase](https://docs.tatnet.ru/docs/platform/supabase),
[Studio](https://docs.tatnet.ru/docs/platform/supabase-studio),
[тариф](https://tatnet.ru/supabase), [изменения платформы](https://tatnet.ru/changelog).
Опубликованные ограничения Free: БД 100 MB, файлы 1 GB, трафик 5 GB/месяц,
Realtime 200 соединений, API 100 запросов/с, приостановка после 7 дней неактивности.
Перепроверить перед выбором тарифа; автоматическая пауза не подходит для обещания постоянной
доступности сайта. Не создавать искусственные запросы для обхода паузы. Платный тариф требует
отдельного решения владельца. Возможность импорта старого Auth больше не является условием:
все аккаунты создаются заново.

## 2. Локальная проверка подготовки — можно выполнять без доступа к сервисам

Из корня репозитория:

```sh
npm ci --ignore-scripts
npm run tatnet:schema:check
npm run test:tatnet
npm run test:auth
npm run lint
npm run type-check
```

После осознанного изменения исходного SQL: `npm run tatnet:schema:build`, затем проверки
и просмотр diff `install.sql`. Генератор и SQL-тесты не используют сеть, текущие ключи,
аккаунты или live-схему. Они проверяют транзакционный отказ на занятой БД, bootstrap,
RLS под разными ролями, CMS, уведомления, Storage, Realtime, бронирования и лояльность.

PGlite моделирует только SQL: Auth issuance, SMTP, реальный JWT/PostgREST, signed URLs,
Storage HTTP, Realtime gateway и настройки Tatnet **не проверены этим тестом**.
Браузерные тесты репозитория используют mock backend и не заменяют проверку Tatnet.

## 3. Установка — ТОЛЬКО после отдельного разрешения

1. В новом пустом Tatnet Supabase вручную закрыть публичную регистрацию и проверить отказ
   signup API на отдельном тестовом адресе. Не менять настройки исходного Cloud.
2. Повторно проверить URL/ref проекта и preflight-условия выше. Выполнить **весь** `install.sql`
   в SQL Editor одной транзакцией, не выделяя отдельные строки. Сохранить только результат
   успешного завершения и версии платформы, без ключей или персональных строк.
3. При ошибке выполнение должно откатиться; закрыть/откатить неуспешную транзакцию в той же
   сессии. Проверить отсутствие частично созданных объектов. Не обходить preflight и не применять
   `DROP/CASCADE` для освобождения места. Если транзакционность Studio не подтверждена — остановиться.
4. Проверить RLS и фактические grants в Studio, buckets `profile-avatars` private / `site-media`
   public, отсутствие пользователей/данных и `app_private.privacy_protection_control.paused=true`.
   Дефолтные привилегии ограничены ролью, запустившей SQL; правила других DDL-ролей платформы
   нужно проверить отдельно. Проверить доступ через реальный API, не только SQL owner.

## 4. Создание единственного администратора

1. При закрытом публичном signup через поддержанный Tatnet Auth Admin UI пригласить/создать
   **новый email/password аккаунт `galstyanwork@gmail.com`**. Проверить поддержку этого пути
   заранее; если UI его не предоставляет — запросить у поддержки безопасный Admin API порядок.
   Нельзя вставлять `auth.users` SQL-строкой или устанавливать фиктивное подтверждение email.
2. Открыть письмо в своём почтовом ящике, подтвердить владение адресом и установить новый пароль
   через защищённый Auth flow. Для нового входа Google не требуется и не настраивается.
   Не передавать пароль, ссылку приглашения, access/refresh token или hash агенту/в PR.
3. Выполнить обычный вход в тестовой сборке; сначала аккаунт должен быть `member`, `/admin/`
   недоступен. Триггер должен создать `profiles` и `user_roles` автоматически.
4. В Studio взять UUID **этого** нового Auth user. В локальной копии `bootstrap-admin.sql`
   заменить единственный nil UUID и выполнить файл владельцем. Не коммитить заполненную копию.
   Скрипт проверяет UUID + точный email, подтверждение, наличие пароля и профиля/роли;
   отказывается заменять другого администратора. Безопасно повторяется для того же UUID.
5. Выйти и войти заново через email/password. Открыть `/admin/`; проверить каталог участников,
   чтение профиля, CRUD синтетической встречи, CMS публикацию и административные уведомления.
   Именно вход через API доказывает работоспособность, SQL owner обходит RLS.
6. Проверить восстановление пароля и отсутствие второго admin. Публичный signup остаётся закрытым.
   Если процедура не сработала, остановиться: не ослаблять RLS и не выдавать клиенту service-role.

## 5. Приёмка перед будущим переключением

Отдельно согласовать staging и создание временных синтетических пользователей. Проверить
через реальные HTTP API: гость / неподтверждённый / участник / другой участник / admin;
чужие профили, роли, посещения, заметки, уведомления, private avatar и private Realtime должны
быть недоступны. Проверить iPhone Safari upload/signed URL, публикацию без утечки черновиков,
шесть посещений и выдачу/погашение награды, сохранение оплаты, вместимость и отмену брони.
Проверить корректность схемы, которую ожидает `admin-client-page.tsx`, без compatibility warnings.
Не удалять тестовые аккаунты или данные без отдельного согласования.

Настройка URL/публичного ключа, callback/recovery, CAPTCHA и сборка для Tatnet — **будущий отдельный
этап**. В этом PR `.env`, hosting, DNS и live Auth не меняются. Сохранять privacy protection
включённой; `paused=true` блокирует новые брони. Открытие регистрации, сбор персональных данных
(включая необязательные поля профиля), бронирований и их правовых условий требует отдельного
решения. Не отключать режим защиты только ради зелёного теста.

После приёмки подготовить diff конфигурации, сборку и план переключения для владельца;
не merge/deploy автоматически. Старый Cloud остаётся доступен для возврата до отдельного
решения. Возврат сайта к предыдущей конфигурации не синхронизирует новые Tatnet-записи:
после начала реального использования требуется план сверки данных. Никакого удаления исходной
БД, переноса DNS, очистки таблиц или автоматического обратного импорта этот PR не выполняет.
