## Границы приложения

- [next.config.ts](next.config.ts): `output: "export"`, `trailingSlash: true`, unoptimized images. [tsconfig.json](tsconfig.json): strict TypeScript, alias `@/*` → `src/*`; корневой `app.js` исключён из TS-проекта.
- [layout.tsx](src/app/layout.tsx): metadata/viewport, canonical-origin script, начальная тема, `BrowserViewerProvider`, общий `PrivacyNotice`. Порядок CSS: [globals](src/app/globals.css) → [business-flow](src/app/business-flow.css) → [design-system](src/app/design-system.css) → [dashboard-experience](src/app/dashboard-experience.css). Смена порядка может изменить несколько разделов.
- [page.tsx](src/app/page.tsx) передаёт статические данные в HomePage. [getViewer](src/lib/viewer.ts) возвращает гостевой placeholder; реальную browser-сессию после hydration определяет provider. Это не SSR-проверка доступа.
- [public-page-shell](src/components/public-page-shell.tsx) соединяет Header/Footer, breadcrumbs и публичную разметку. [structured-data](src/components/structured-data.tsx) выводит JSON-LD.
- В текущем `src/app` нет `route.ts`/`route.js` и runtime Next.js API. Статические auth URL — страницы, работающие в браузере. Не проектировать исправление вокруг несуществующего `/api/...`.
- Supabase Auth/PostgREST/Storage/Realtime — внешняя граница. Singleton [client](src/lib/supabase/client.ts) использует [fetch](src/lib/supabase/fetch.ts) с timeout/abort и privacy guard; это не серверный firewall.
- Root [index.html](index.html), [app.js](app.js), [styles.css](styles.css), [privacy.html](privacy.html), [terms.html](terms.html), [cookies.html](cookies.html) — отдельная реализация. npm build собирает Next.js source, а не эти файлы. Внешние потребители legacy-файлов здесь не проверялись; не удалять их автоматически.

## Аутентификация и безопасность

| Файл | Что делает / где править |
|---|---|
| [supabase/client.ts](src/lib/supabase/client.ts) | Один browser client, persistSession/autoRefreshToken, localStorage и PKCE; при недоступном хранилище возвращает null. `detectSessionInUrl:false`: не добавлять второй автоматический exchange |
| [use-browser-viewer.ts](src/hooks/use-browser-viewer.ts) | Context и Auth subscription; подтверждённая личность отображается до optional profile/role/notifications enrichment. Защита от устаревших async результатов; shared event read state |
| [viewer.ts](src/lib/viewer.ts) | Типы Viewer/ViewerRole и статический guest; не источник реальной авторизации |
| [email-auth-form.tsx](src/components/email-auth-form.tsx) | Login/signup/recovery/resend, validation, CAPTCHA, cooldown, защита от повторной отправки и enumeration; в privacy mode регистрационные поля скрыты |
| [auth-captcha.tsx](src/components/auth-captcha.tsx), [auth-password-input.tsx](src/components/auth-password-input.tsx), [auth-profile-fields.tsx](src/components/auth-profile-fields.tsx) | Turnstile и input UI; public site key не заменяет provider secret |
| [registration.ts](src/lib/registration.ts) | Поля/validation/TERMS_VERSION; наличие terms checkbox не доказывает отдельное согласие на все цели обработки |
| [auth-dialog.tsx](src/components/auth-dialog.tsx) | Модальное email access; Header/Home используют общий auth UI |
| [email-link-confirmation.tsx](src/components/email-link-confirmation.tsx), [auth-link.ts](src/lib/auth-link.ts) | Проверка type/hash и явный verifyOtp; не потреблять single-use ссылку незаметным prefetch |
| [auth/callback/page.tsx](src/app/auth/callback/page.tsx), [auth-redirect.ts](src/lib/auth-redirect.ts) | PKCE code exchange, legacy recovery compatibility и ограничение destinations; не открывать произвольные next URLs |
| [password-reset-form.tsx](src/components/password-reset-form.tsx) | Проверка recovery flow, смена пароля существующему user, local sign-out; не создавать replacement account |
| [profile-onboarding.ts](src/lib/profile-onboarding.ts) | Решение о завершённости onboarding и landing destination |
| [auth-ui.ts](src/lib/auth-ui.ts), [auth-aware-cta.tsx](src/components/auth-aware-cta.tsx), [auth-aware-content.tsx](src/components/auth-aware-content.tsx) | Презентация действий по текущему viewer, не выдача прав |

Email/password — текущий видимый интерфейс. Существующие OAuth/Google identities учитываются в recovery/совместимости, но legacy env flags не означают наличие кнопок Google/Telegram. [admin.ts](src/lib/admin.ts) содержит email helper, однако активный admin loader проверяет `user_roles`; не превращать frontend allowlist в авторизацию и не копировать реальные адреса в документы.

Авторитетные правила: `auth.users`/identities у Supabase, `public.user_roles` и `app_private.is_admin()`, RLS, column grants и guarded RPC. `user_metadata` годится для отображаемого имени, но редактируется пользователем и не может выдавать admin. Чтение directory идёт через guarded `admin_member_directory`, а не прямое чтение Auth users из браузера. Проверять фактическое определение БД только при разрешённой задаче.

Почта: [supabase/auth-email-config.mjs](supabase/auth-email-config.mjs) → [generate-auth-emails](scripts/generate-auth-emails.mjs) → [templates](supabase/templates). Семь типов: verification, reset, email change, magic link, invitation, reauthentication, password changed. [update-supabase-auth-email-config](scripts/update-supabase-auth-email-config.mjs) готовит конфигурацию, не означает установленную live SMTP/templates. Инструкция и известные ограничения: [BRANDED-AUTH-EMAILS](docs/BRANDED-AUTH-EMAILS.md), [EMAIL-AUTH-SETUP](docs/EMAIL-AUTH-SETUP.md).

## Профиль и Storage

[profile-form.tsx](src/components/profile-form.tsx) сохраняет базовый профиль, поддерживает onboarding, crop/upload/remove и ссылку на подготовку privacy request. [avatar-image.ts](src/lib/avatar-image.ts) проверяет реальные байты/MIME, декодирует на устройстве, подготавливает JPEG через canvas; HEIC зависит от native decoder. Проверка в Chromium не доказывает работу на физическом iPhone Safari.

Private bucket — `profile-avatars`; исторический ключ `${userId}/avatar.webp` сохраняется даже для JPEG MIME, потому что связан с SQL-проверками. Не менять суффикс/путь как косметический рефакторинг. Signed URLs создаются через Storage SDK. Миграция: [add_profile_avatar_storage](supabase/migrations/20260726214531_add_profile_avatar_storage.sql). Публичные `site-media` используются CMS отдельно; приватные фото туда не переносить.

Опасные границы: on-delete cascade от Auth может затронуть несколько таблиц, а restrict блокирует удаление связанных meetup/attendance/booking. Никогда не «исправлять» FK удалением пользователя/истории. Private admin notes не должны попадать в member select.

## Встречи, записи, посещения и лояльность

Публичный поток: [meetups-listing](src/components/meetups-listing.tsx) → [fetchUpcomingPublishedMeetups](src/lib/meetup-data.ts) → `meetups` и собственные booking statuses. Listing поддерживает `?id=`/`?meetup=` выбор события. При включённой privacy protection listing показывает паузу и не загружает расписание.

[meetup-booking-button](src/components/meetup-booking-button.tsx) вставляет только meetup_id; Auth default/DB определяют user. Отмена обновляет status собственной confirmed записи. Capacity, окно и статус события проверяются SQL, а не счётчиком в UI. Важные места: `guard_booking_updates`, `sync_booking_capacity` в [phase 1](supabase/migrations/20260723131156_phase_1_member_meetups_loyalty.sql), [capacity guard fix](supabase/migrations/20260824193758_fix_member_booking_capacity_guard.sql), отдельный privacy trigger.

[meetup-time.ts](src/lib/meetup-time.ts) отвечает за Europe/Moscow, перевод wall-time ↔ ISO и booking state; админская форма использует эти helpers. Цены сериализуются в minor units; не вводить новую денежную единицу только в UI.

[admin-dashboard](src/components/admin-dashboard.tsx) пишет attendance/payment и специальные награды. SQL `reconcile_loyalty_rewards` сериализует расчёт, каждые шесть оплаченных посещений формируют reward sequence; redemption защищён [business flow](supabase/migrations/20260817090000_complete_meetup_business_flow.sql). UI [loyalty-progress](src/lib/loyalty-progress.ts) считает attended + payment_status=paid и доступные неистёкшие награды. Истинные начисления/погашения остаются в БД; не заменять их вычислением UI и не стирать оплаты при повторном check-in.

## Вопросы, прогресс и избранное

- [questions.json](src/data/questions.json) → [questions.ts](src/lib/questions.ts): bundled questions, категории, уровни, IDs и переводы. Не перенумеровывать ID при редактировании текста: account progress/favorites хранят эти значения.
- [question-deck.tsx](src/components/question-deck.tsx): выбор/фильтры, random, навигация, избранное, copy и показ перевода; использует [use-question-state.ts](src/hooks/use-question-state.ts) и типы [question-sync.ts](src/lib/question-sync.ts).
- Hook хранит guest state в versioned localStorage; обычный signed-in режим загружает own tables, импортирует guest state, повторяет pending writes и слушает private Realtime channel. Учет timestamps и [latest-write-wins SQL](supabase/migrations/20260828002000_enforce_latest_question_sync_wins.sql) нельзя удалять как лишнюю сложность.
- **Privacy mode:** hook работает как local-only practice; не импортирует/не стирает облачную историю. При этом account dashboard отдельно читает прежние cloud counters. Не обещать синхронизацию во время паузы.
- Admin CRUD `managed_questions` находится в AdminDashboard, но [getManagedQuestions](src/lib/managed-questions.ts) сейчас возвращает `[]`. Наличие CRUD не доказывает публикацию этих вопросов в публичную колоду.
- Контентные проверки: [validate-questions](scripts/validate-questions.mjs), [validate-translations](scripts/validate-translations.mjs); account-sync поведение проверяется auth browser suite и SQL.

## CMS, медиа и SEO

[content-editor.tsx](src/components/content-editor.tsx) подключён из AdminDashboard; редактирует draft/published site_content, FAQ и revisions, вызывает `publish_site_page`, `discard_site_page_drafts`, `restore_site_revision`. <a id="privacy"></a>
## Режим защиты персональных данных

[privacy-protection.ts](src/lib/privacy-protection.ts): включён по умолчанию, только точное значение `NEXT_PUBLIC_PRIVACY_PROTECTION_MODE=disabled` открывает прежнее frontend поведение. Это build-time выбор, нужна пересборка.

[PrivacyNotice](src/components/privacy-notice.tsx), форма/CTA, listing и question hook реализуют паузу/локальную практику. [SDK fetch](src/lib/supabase/fetch.ts) блокирует signup/OTP и POST/PUT bookings до передачи тела. Его можно обойти независимым HTTP-клиентом: **не выдавать эту защиту за закрытый Auth API**.

[privacy-protection-review.sql](supabase/operations/privacy-protection-review.sql) создаёт закрытый control flag/booking trigger с own cancellation и admin bypass. Это отдельная operation, не стандартная migration; напрямую Auth signup она не закрывает. Provider `disable_signup` устанавливается отдельно с сохранением existing login/providers/recovery.

[privacy-request-tool](src/components/privacy-request-tool.tsx) готовит и копирует текст на устройстве; это не backend submission, не автоматическое удаление и не готовый частный канал оператора. Деактивация, отзыв согласия, erasure и обязательное хранение различаются.

[PRODUCTION-CHANGE-RU](docs/privacy/PRODUCTION-CHANGE-RU.md) фиксирует ранее разрешённое применение booking SQL и тогдашний открытый Auth. [OPERATIONS-RU](docs/privacy/OPERATIONS-RU.md) и [REPORT-RU](docs/privacy/REPORT-RU.md) содержат исходный план/срез; это исторические записи, не текущий health check. Нельзя повторять SQL или переключать Auth только потому, что runbook существует.

Изменение кода/merge не применяет DB migrations, operator SQL, SMTP/templates, Auth settings, NS/DNS или SSL. <a id="risks"></a>
## Проверенные расхождения и обслуживание карты

1. **Старая документация:** [CODEBASE-MAP](docs/CODEBASE-MAP.md) и вводная README описывают Vercel/server API; текущие next.config/readers показывают static export/browser Supabase. Старые документы сохранены; не копировать их как новую архитектурную истину.
2. **Комментарии против реализации:** server-like названия public loaders и комментарии CMS обещают больше, чем текущие stub returns. Проверять imports/возвращаемые значения и конкретного reader перед изменением.
3. **Source vs live:** миграция personal fields и operator privacy SQL находятся в разных механизмах доставки. UI fallback/исторический отчёт не доказывают актуальную live схему. В этой задаче нет fresh DB/config проверки.
4. **Две реализации:** корневые HTML/JS и `src` могут расходиться; изменять активный npm build source. Наличие public settings в legacy/Vercel файлах не повод переносить туда секреты или менять providers.
5. **Безопасность в браузере:** localStorage-сессия требует аккуратной работы с XSS; frontend guards не заменяют RLS/Auth. Auth deletion имеет последствия для FK и истории; не использовать как recovery.
6. **CMS/managed questions:** admin CRUD не равен гарантированной публичной публикации при пустых loaders/privacy pause. Partial EN/RU не равно полному переводу продукта.
7. **Эксплуатация:** нет закреплённого engines и checked-in CI deployment; наличие зелёных mock tests не доказывает готовность hosting, DNS, SMTP и реального admin входа. Не расширять документационную задачу до исправления этих настроек.

При изменении архитектуры: обновить baseline, route catalogue, feature lookup и соседние ссылки; убрать/переписать устаревший тезис в новых навигационных файлах, а historical reports помечать историческими. Проверять существование всех относительных ссылок/anchors, соответствие script names manifest и отсутствие credential values. Новые подробные runbooks связывать ссылками, не размножать в INDEX. Сначала исправлять источник и подтверждать behavior; документация не должна маскировать неисправность кода.
