## Проверенная архитектура и ограничения

База проверки — `timeweb-static` после PR #8, отдельная ветка `codex/privacy-protection-review`. Статический Next.js export на Timeweb, браузер напрямую обращается к Supabase Auth/PostgREST/Storage/Realtime. Исполняемых серверных API в статическом экспорте нет. Значит middleware сайта и российский прокси не перекрывают известный публичный адрес Supabase.

Read-only metadata проекта подтвердили `eu-west-3` (Париж), PostgreSQL 17.6, активный проект. Первичные Auth, БД и Storage находятся в выбранном регионе; по [официальному FAQ Supabase](https://supabase.com/legal/privacy-resources/data-residency-and-transfers-faq) там же находятся резервные копии, но сроки зависят от плана. Телеметрия, поддержка и CDN могут обрабатываться вне региона. План, фактические резервные копии и договорные адреса ЦОД не проверены. Пользовательские строки, содержимое файлов, пароли и токены не выгружались.

На всех 29 найденных таблицах public/storage включён RLS. Это не доказательство достаточности каждой политики. Проверены определения политик, grants и ключевых функций; локальные SQL-тесты проверяют собственные/чужие записи и запрет повышения роли. `admin_member_directory` и `admin_publish_announcement` доступны authenticated, но обе живые функции имеют внутреннюю проверку `app_private.is_admin()`. Предупреждение Security Advisor о SECURITY DEFINER не равно найденной утечке. Не убирать grants вслепую: это сломает администратора. Локальный тест подтверждает отказ обычному участнику; реальный сеанс существующего администратора после изменений требует ручной проверки.

`profile-avatars` — закрытый bucket, доступ по владельцу/администратору и подписанным URL. `site-media` — публичный: туда нельзя помещать приватные фотографии/документы. Путь аватара привязан к UUID; не переименовывать при миграции. Защита от утёкших паролей в Auth выключена: рассмотреть после проверки тарифа и дополнительного обработчика; автоматически не включалась.

## Реальные изменения в PR

- `src/lib/privacy-protection.ts`: закрыто по умолчанию; только точное build-time `disabled` разрешает старый режим. Смена переменной требует пересборки.
- `src/lib/supabase/fetch.ts`: общая защита SDK от signup/OTP и POST/PUT bookings до отправки тела. Не является сетевым firewall и не защищает отдельный HTTP-клиент.
- Форма регистрации не собирает поля, гостевые CTA ведут на вход, двуязычное уведомление на страницах. Вход/выход, refresh, подтверждение и восстановление существующих аккаунтов сохранены.
- Новая запись заблокирована; отмена существующей доступна. Dashboard/права не менялись. На публичных meetup-страницах при паузе нет фоновой выборки Supabase. Вопросы продолжают работать локально без отправки прогресса; сохранённые облачные записи не удаляются.
- `/privacy-requests/`: локальная подготовка четырёх видов обращения без сбора идентификаторов и без отправки в общую Telegram-группу. Из профиля ссылка ведёт туда.
- `supabase/operations/privacy-protection-review.sql`: только согласуемая операция, не автоматическая миграция; сохраняет RLS и историю, допускает отмену собственной записи и работу администратора, запрещает прямой insert/reactivation участнику.
- Diagnostics понимают режим защиты; отдельная read-only проверка не печатает секреты и не создаёт тестового пользователя. В build status добавлен режим privacy.
- Новые SQL/unit/browser проверки. Полный список изменённых файлов — в diff PR. Итоги запусков — [VALIDATION.md](VALIDATION.md).

## Правовая оценка и открытие

Проверены текущие публикации: [152-ФЗ, Минтруд](https://mintrud.gov.ru/docs/laws/130), [23-ФЗ](https://publication.pravo.gov.ru/document/0001202502280034), [156-ФЗ](https://publication.pravo.gov.ru/document/0001202506240021). Портал опубликования и форма РКН при прямом запросе давали timeout; текст изменений сопоставлен с консолидированной публикацией. Перед подачей нужна повторная проверка формы и действующей редакции.

Ст.18(5) после изменений 2025 ограничивает перечисленные операции сбора с использованием зарубежных БД; узкие исключения оценить с юристом. Прямая первичная запись из браузера в Париж — основание не открывать сбор российских данных. Копия в России или российский reverse proxy сами по себе проблему не решают. Ст.22 предусматривает уведомление, ст.12 — отдельный режим трансграничной передачи. Там, где требуется согласие, оно оформляется отдельно; договор и обязанность по закону могут быть иными основаниями. Согласие на рекламу не объединять с доступом к услуге. Не обещать отсутствие санкций за прошлую обработку.

Владелец — физическое лицо на НПД, не ИП (по сообщению владельца); не писать «ИП» в документах. Фото не объявляется автоматически биометрией: требуется оценить цель идентификации. Нужны решения по несовершеннолетним и специальным категориям, уровень защищённости/модель угроз, организационные меры по применимым нормам. Наличие английского интерфейса само по себе не доказывает применимость GDPR.

Открытие: согласованная российская архитектура → проверенные резервные копии/восстановление и RLS → утверждённые основания/минимизация/сроки/документы → уведомления и договоры → тесты реального существующего admin/email/recovery → отдельное разрешение владельца. Успех технических тестов не означает юридическое соответствие.

## Что требует отдельного разрешения

1. Изменить только Auth `disable_signup` на `true`, сохранив email provider, пароли, SMTP, confirmation и recovery. Проверить дополнительные способы создания пользователей (OTP, OAuth неизвестной личности, anonymous, invite), не отключая вход существующего администратора.
2. После backup/preflight применить reviewed booking operation; выполнить отрицательные проверки API на изолированном стенде. В production не создавать аккаунты ради проверки без разрешения.
3. Развернуть собранный privacy mode. Это отдельное разрешение на deployment, не подразумевается открытием PR.

Миграция, новый SMTP, изменение сроков/удаление данных, публикация юридических документов и любые обращения в РКН — отдельные решения. Пока рабочая инфраструктура не изменена, нельзя утверждать, что публичный сбор остановлен.
